### 跨平台约束

本项目最初在 Windows 上开发，当前在 macOS 上继续。本轮改动已按此约束审查：

- 无本机绝对路径、无 Homebrew/`/tmp` 路径进入仓库。
- `package.json` 改动仅为在测试清单里追加文件名，未引入 shell 专有语法。
- `scripts/run-rag-service.mjs` 原本就有 `win32` 分支（`.venv/Scripts/python.exe`，回退 `python`），未改动。

仍存在的既有隐患（本轮未擅自处理）：仓库没有 `.gitattributes`。跨平台协作时行尾策略完全依赖各机 `core.autocrlf`。补一份会一次性重写全仓行尾并产生巨大 diff，属需要决策的动作，建议单独排期。

## 二、已修复：批次 H（Agent 明确缺陷）

| ID | 问题与实际改动 |
|----|----------------|
| **H1-VERSION-QUOTA** | `repositories/agents.ts` 的版本配额把 `latest_version + 1` 当作数量比较（`nextVersion > maxVersionsPerAgent`）。版本号单调不减，因此一个 Agent 被编辑 100 次后**永久无法再编辑**，即便裁剪旧版本也救不回来。改为 `select count(*) from agent_versions where agent_id = $1` 按行数计数、以 `>=` 判定；版本号仍保持 `latest_version + 1` 单调，因为它是版本在审计中的身份。 |
| **H2-PUBLISH-DISABLED** | `publishAgentForUser` 的 SQL 无 status 守卫，无条件 `status = 'published'`。对一个已 `disabled` 的 Agent 调用 publish 会静默复活它，等于绕过运维的停用开关且无审计痕迹。SQL 加 `and status <> 'disabled'`；为了不把「已停用」误报成「不存在」，未命中时回查一次 status，是 disabled 则抛 `AGENT_DISABLED`，服务层映射为 409（`Enable the agent before publishing it`）而非 404。 |
| **H3-TOOL-ERROR-CODE** | 自定义工具的所有失败在 `agent-run.service.ts` 被压成同一个字符串 `'Tool execution failed'` + step `{error:'tool_execution_failed'}`。白名单拒绝、超时、响应超限、JSON 非法、`response_path` 未命中、MCP 协议错误、MCP 工具自报错误全部同一个标签，运维分不清是配置错误还是上游抖动，模型也分不清该改参数还是该重试。新增 `runtime/agent-tool-error.ts`：`AgentToolError`（`code` + 调用方安全的 message + 可选 details）、15 个稳定错误码、`classifyAgentToolError()`（含 undici `cause.code` 透传、`TimeoutError`/`AbortError` → `tool_timeout`、`SyntaxError` → `tool_response_invalid_json`）。`remote-endpoint.ts` / `custom-http-tool.ts` / `custom-mcp-tool.ts` 内所有 `throw new Error` 全部替换为带码抛出；run loop 把 code 同时写入 step output、SSE `tool.failed` 事件与喂给模型的 tool 结果。 |

错误码清单（属 step output 契约，只允许增量扩展）：`tool_input_invalid`、`tool_endpoint_not_allowlisted`、`tool_endpoint_unsupported_protocol`、`tool_endpoint_credentials_insecure`、`tool_endpoint_blocked_address`、`tool_endpoint_misconfigured`、`tool_timeout`、`tool_network_error`、`tool_http_status`、`tool_response_too_large`、`tool_response_invalid_json`、`tool_response_path_missing`、`tool_mcp_protocol_error`、`tool_reported_error`、`tool_execution_failed`。

## 三、已修复：批次 I（摄取侧数据完整性）

| ID | 问题与实际改动 |
|----|----------------|
| **I1-TOKEN-COUNT** | `file_chunks.token_count` 自 `0032` 迁移起就存在且带 check 约束，但 `rag-service/db.py` 的两处 INSERT 只把它写在 `returning` 列表里、**不在 INSERT 列清单中**，因此每一行读回来都是 NULL。两处 INSERT 补上列与绑定值。计数由新增的 `chunk_strategy.estimate_token_count()` 产生——这是一个刻意近似的估算器（CJK/假名/谚文按字计，其余按 4 字符 1 token 向上取整），因为在用的 embedding/chat 供应商都不暴露真实分词器。`0043` 迁移给该列加了 comment 明确写出「不是精确分词结果」与估算器标识 `heuristic-cjk-v1`。 |
| **I2-CHUNK-VERSION-DRIFT** | `CHUNK_STRATEGY_VERSION` 字符串里手写着 `chunk1000-overlap100`，而实际切块参数是 `ingestion.py` / `converted_ingestion.py` 里各自独立的字面量 `1000` / `100`。改动切分器而忘记改字符串，会让所有陈旧 Chunk 继续宣称自己是当前策略，重建永远不会被触发。新增零依赖模块 `rag-service/chunk_strategy.py` 作为唯一来源：`CHUNK_SIZE` / `CHUNK_OVERLAP` → 派生 `CHUNK_PARAMETER_SUFFIX` → 派生 `CHUNK_STRATEGY_VERSION`；`db.py` 改为 import 并重导出（`db.CHUNK_STRATEGY_VERSION` 对外不变）；两个切分器改用共享常量。`LEGACY_CHUNK_STRATEGY_VERSION` 保持字面量不动——它指代已存储的历史数据，绝不能被当前参数重新派生。测试同时钉住当前取值，使参数变更成为一次需要配套重建计划的显式动作。 |
| **I3-WARNING-DETAIL** | 两个问题。其一：转换警告只有计数落 PG（`warning_count`），警告文本只存在对象存储的 manifest 里，运维要回答「这个文件为什么是 `completed_with_warnings`」必须逐个下载并解码 artifact。新增迁移 `0043_conversion_warning_details.sql`，给 `file_conversion_generations` 加 `warnings text[]`，并加约束保证非空数组的元素数与 `warning_count` 一致（历史行是空数组 + 非零计数，故只约束非空情形）。`complete_conversion_generation` 的签名从 `warning_count: int` 改为 `warnings: Iterable[str]`，计数由代码派生，杜绝两者不一致；新增 `_require_warning_codes()` 拒绝空白与超 200 字符的条目，防止转换器把无界文本塞进运维列。其二：`converters/spreadsheet.py` 无条件把 `CSV_DELIMITER:<name>` 当作 warning，导致**每一个 CSV 都是 `completed_with_warnings`**，这个状态因此失去意义、真正转换有损的文档被淹没。分隔符是溯源信息而非缺陷，manifest 新增 `notes` 字段承载它（`notes` 不影响文件状态），`converters/base.py` 的三个转换助手把 `notes` 一路透传。 |

## 四、已修复：批次 J（Schema 与检索细节）

| ID | 问题与实际改动 |
|----|----------------|
| **J1-PATTERN-SUPPORT** | JSON Schema 子集不支持 `pattern`，工具作者无法约束字符串格式，模型传错格式只能等下游端点返回 400。现已支持，但**仅对工具输入 schema 开启**（`AgentSchemaDefinitionOptions.allowPattern`，默认关闭）。Agent 输出 schema 不开：`buildAgentJsonInsufficientEvidenceOutput` 必须能合成一个满足 schema 的拒答占位值，而任意正则无法保证被通用占位值满足——一旦开启，恰恰在需要拒答时拒答会失败。用户自定义正则运行在服务进程内且 JS 无法中断已启动的正则匹配，因此防护是首要设计：静态筛查拒绝「无界量词套无界量词/交替」（`(a+)+`、`([a-z]+)*`、`(?:x|xy)+`）、回溯引用、lookahead/lookbehind、命名组与非 `(?:` 的组修饰符；有界重复（`(?:\d{3})+`、`(?:a+){3}`）仍可用。另有 pattern 长度 200 上限、被检字符串 4096 上限、256 条有界编译缓存。**实施中发现的关键点**：`validateAgentJsonSchemaValue` 会在执行期重新校验一次 schema 定义，必须把 options 一并透传，否则合法创建的带 `pattern` 工具会在调用时被拒；`validateAgentJsonSchemaInput` 作为工具输入入口固定传 `allowPattern: true`。 |
| **J2-PLANNED-QUERY-STARVATION** | `agentic_retrieval._planned_queries` 把候选拼成 `[query, *LLM 语义变体, *确定性计划]`，`max_queries=3` 时只要改写器返回 2 个变体，**确定性计划整体被挤出请求**。被挤掉的恰好包含 exact-marker 查询——字面标识符（订单号、错误码）的召回依赖它，而且确定性计划不依赖某次 LLM 调用是否成功或是否跑偏。改为：原始问法固定第一位，其余预算由确定性计划与 LLM 变体 `zip_longest` 轮转分配，每轮确定性优先（只剩一个槽位时给不依赖外部调用的那一路）。 |
| **J3-ANALYZER-NAMING** | ES mapping 里的 analyzer 名叫 `chatllm_mixed_text`，实际定义是 `{"type": "standard"}`，不做任何中文分词；混合语种覆盖其实来自各文本字段的 `.cjk` 子字段（内置 `cjk` bigram analyzer）。**决定不重命名**：analyzer 名是 index settings 的一部分，改名即改 mapping，会让所有既有部署被迫全量重建 BM25 索引，代价远超收益。改为在 `keyword_store.py` 定义处写清它到底是什么、CJK 覆盖真正来自哪里、真分词需要什么前置条件，并说明为何保留这个名字。真正的中文分词见下方 `B2`。 |

## 五、撤销的误判

| ID | 说明 |
|----|------|
| **W1-CHECKPOINT-LEASE** | 深度分析当时认为 `rag-service/db.py` 的 `update_ingestion_job_checkpoint` 只更新 `heartbeat_at` 而不续 `lease_expires_at`，长耗时单步有被抢占风险。**该判断错误。** `server/src/services/fileQueue.ts:53-87` 有 `startFileIngestionHeartbeat`，在整个摄取过程中每 `FILE_QUEUE_STALE_AFTER_MS / 3` 调用一次 `renewFileIngestionLease`。租约由服务端编排者持有并续期，rag-service 的 checkpoint 只负责推进进度与刷新 `heartbeat_at`——这是分工设计，不是缺陷。未做任何改动。 |

## 六、经评估决定不改的项

这些在深度分析中被点出，但评估后认为改动代价或风险高于收益，记录理由以免后人重复讨论：

| 项 | 不改的理由 |
|----|-----------|
| `citation_score` 命名误导 | 它并非真正的引用分。但重命名会破坏 API 兼容；代码中已有 `applicable: False` 与 `legacy_provenance_alias` 标注说明其性质。 |
| `key_term_coverage` 采用全集合口径 | 改口径会连带改变所有已校准的质量阈值，风险高于收益。 |
| 内置工具风险等级全为 `read` | **不是缺陷**——它们确实只读。真实问题是 UI/文档让人误以为 `writes` 策略对内置工具有保护作用，属文案问题。 |
| 取消/审批重复请求返回 409 | 改为幂等需先确认既有测试是否依赖 409 语义，本轮未展开。 |

## 七、基础设施阻塞项（本轮无法在代码内解决，正式立项）

以下 4 项**没有做任何假装修复的改动**。每项都需要代码之外的前置条件。

### B1-PDF-OCR：扫描版 PDF 无文本层时无法摄取

- **现状**：`converters/pdf.py` 依赖 PDF 自带文本层。完全没有可提取文本时以 `PDF_HAS_NO_EXTRACTABLE_TEXT` 直接拒绝；部分页无文本时产出 `PDF_SOME_PAGES_HAVE_NO_EXTRACTABLE_TEXT` 警告。扫描件、图片型 PDF 实际上无法进入知识库。
- **前置条件**：需要引入 OCR 引擎（Tesseract / PaddleOCR / 云 OCR）。这不是加一个 pip 包就完事的决策：涉及镜像体积与构建时间、CPU/GPU 资源、按页耗时对摄取租约与超时的影响、中文识别质量、以及云 OCR 时的数据出境合规。
- **影响面**：`converters/pdf.py`、`ConversionLimits`、摄取超时与租约参数、`document-types.json` 的能力声明、镜像与依赖锁。
- **建议**：先做产品决策（是否支持扫描件、可接受的延迟与成本），再定引擎。落地时应作为独立的 `conversion_profile`（如 `pdf-ocr-v1`）而非替换现有 `pdf-text-v1`，以便两条路径共存并按需路由。

### B2-ES-CHINESE-ANALYZER：BM25 无真正的中文分词

- **现状**：主文本字段用 `standard` analyzer（对 CJK 按字切分），配合 `.cjk` 子字段的内置 bigram analyzer。对中文查询而言，词级匹配质量明显弱于装了分词插件的集群，长词与专有名词的 BM25 首轮召回受损。见上方 `J3`。
- **前置条件**：需要在 Elasticsearch **集群**上安装插件（`analysis-ik` 或 `analysis-icu`）。这是运维动作，代码无法完成；插件版本必须与 ES 版本严格匹配。
- **影响面**：`keyword_store.py` 的 index settings/mapping、`settings.elasticsearch_schema_version` 需要 bump、**所有既有部署需全量重建 BM25 索引**、`docker-compose.yml` 当前是官方 `elasticsearch:8.15.3` 裸镜像（无任何分词插件），需换成带插件的自构镜像。
- **建议**：与 `B3` 合并到同一个「索引重建窗口」执行，避免两次全量重建。上线前用中文查询集做 A/B，确认召回提升足以偿付重建成本。

### B3-MILVUS-GENERATION-FIELD：向量库缺 `conversion_generation_id`

- **现状**：PG 的 `file_chunks` 有 `conversion_generation_id`，检索时能按活跃 generation 做权威过滤；Milvus collection 的 schema 里没有这个字段。向量召回无法在库内直接按 generation 过滤，只能依赖回 PG 校验（`_active_cached_documents` 正是在做这件事）。这不是正确性漏洞，但多了一次往返，且旧 generation 的向量在被清理前会参与打分。
- **前置条件**：Milvus 加字段需要重建 collection 并全量重新灌入向量，无法在线 alter。
- **影响面**：`vector_store.py` 的 schema 定义与插入/检索路径、collection 迁移脚本、全量重新 embedding 的时间与 API 成本（按文档量计）。
- **建议**：与 `B2` 共用同一个重建窗口。迁移前先量化收益：如果回 PG 校验的延迟占比很小，这项可以长期搁置。

### B4-QUALITY-SCORE-CALIBRATION：检索质量分未经校准

- **现状**：`evaluation.py` 的质量分与各处阈值来自工程直觉，没有标注数据支撑。无法回答「分数 0.62 到底意味着什么」，也无法判断阈值调整是改善还是恶化。
- **前置条件**：需要一份带人工相关性标注的评测集（query × chunk 相关性判定）。这是数据标注工作，不是代码工作。
- **影响面**：`evaluation.py` 的评分与阈值、`rag_eval_*` 相关表与报表、`docs/rag-architecture-v2.md` 中的质量口径描述。
- **建议**：先积累线上真实查询样本，抽样标注 200–500 条形成基准集；有了基准才谈校准。在此之前不要凭感觉调阈值——现有阈值虽未校准，但已与现有测试快照绑定，盲调会让快照失去参照意义。
