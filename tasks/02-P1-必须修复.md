## P1-TRUNCATE-RUN 重新生成不会取消仍在执行的 Agent Run

- **模块：** Agent / Chat
- **位置：** `server/src/repositories/messages.ts`（约 324–329 行）、`client/src/stores/useChatStore.ts`（`regenerateMessage`，约 545–581 行）
- **关联：** `server/src/repositories/agentRuns.ts` 的 `completeAgentRunForUser`；迁移 `0036` 中 `assistant_message_id` / `user_message_id` 为 `ON DELETE SET NULL`

### 场景

用户在已绑定 Agent 的会话里点「重新生成」。客户端先 `DELETE .../truncate`，再把最后一条用户消息重发。

### 根因

`truncateConversationFromUserMessage` 只删除 `created_at >=` 的消息，**从不**调用 `cancelAgentRunForUser`。消息删掉后 Run 行仍是 `running` / `waiting_approval`。旧 Run 结束后，若 `assistant_message_id` 已空，`completeAgentRunForUser` 会 **重新 insert 一条助手消息**，污染已经截断并开始新 Run 的会话。

删除单条助手消息、删除会话若也不取消活跃 Run，属于同一类生命周期漏洞，应一并处理。

### 预期

截断、删除消息、删除会话时：

1. 该范围内所有非终态 Run（`queued` / `running` / `waiting_approval`）进入 `cancelled`
2. 进程内 abort 信号触发，停止后续模型/工具调用
3. 不得在截断后的会话里再插入旧 Run 的助手消息

### 建议改法

- 在 truncate / delete-message / delete-conversation 的同一事务里取消相关 Run（按 `conversation_id` + 消息时间窗或 message id）
- 完成后若发现 `assistant_message_id` 为空，禁止再 insert 助手消息
- 客户端 `regenerateMessage` 可额外先调 cancel，但 **不能只靠前端**；服务端必须兜底

### 验收

- [ ] Agent 会话再生：旧 Run 为 `cancelled`，会话里只有新 Run 的助手消息
- [ ] 旧 Run 的 HTTP/MCP 工具在 cancel 后不再发出新请求
- [ ] 删除会话后无残留 `running` Run
- [ ] 集成测试覆盖 truncate × 活跃 Run（见 07）

## P1-LENGTH-TOOLS `finish_reason=length` 仍会执行残缺工具调用

- **模块：** Agent 运行时
- **位置：** `server/src/modules/agents/agent-run.service.ts`（约 914–1008 行）
- **关联：** `assertAgentStreamComplete`；注释已强调截断流对 Agent 的风险

### 场景

模型在生成 `tool_calls` 参数时触达 `max_tokens`。OpenAI 兼容协议返回 `finish_reason: "length"`，`tool_calls` 可能残缺。

### 根因

仅在 `toolCalls.length === 0` 时把 `length` 当资源上限失败。有 tool_calls 时直接进入审批/执行。残缺 JSON 多数会进失败分支，但 **恰好仍可 parse 的截断对象** 会带着错误参数去打 HTTP/MCP。写工具尤其危险。

### 预期

任何 `finish_reason === 'length'`（以及无法证明完整的流）都不得执行工具。应记为资源上限失败，不进入审批。

### 建议改法

在解析 tool_calls 之前拦截 `length` / 空 `finish_reason`。现有 `assertAgentStreamComplete` 只保证有 finish_reason，还要禁止「带工具的 length」。

### 验收

- [ ] 单测：`length` + 可解析残缺 arguments → 不调用 `execute`
- [ ] 单测：`length` 且无 tool_calls → `AgentResourceLimitError`
- [ ] 正常 `finish_reason=tool_calls` 不受影响

## P1-DELETE-CACHE 删除文件后缓存窗口仍可复用已删证据

- **模块：** RAG / 清理
- **位置：**
  - `server/src/repositories/cleanupJobs.ts`（`prepareFileCleanup`，约 240–248 行）
  - `rag-service/main.py`（`/cleanup-file`，约 455–466 行）
  - `rag-service/agentic_retrieval.py`（`_evaluate_cached_documents`，约 383–396 行）
- **关联：** `rag-service/db.py` 的 `bump_project_knowledge_version`；精确缓存 key 绑定 `knowledge_version`

### 场景

用户删除文档。`files.status` 立刻变为 `deleting`，但 `knowledge_version` 要等异步 worker 调用 `/cleanup-file` 成功才 +1。窗口可达数秒到数分钟。同一用户用相同问题再检索时，精确缓存命中 **不走** `get_active_chunks_by_ids` 权威校验，继续返回已删文件内容。新检索会因 `status='completed'` 过滤掉该文件，缓存短路绕过了这一点。

### 预期

文件进入 `deleting` 后，任何检索（含缓存命中）都不得再把该文件当作证据。宁可 cache miss，不可引用已删内容。

### 建议改法（择一或组合）

1. **推荐：** `prepareFileCleanup` 与 bump `knowledge_version` 同临界区（至少在标 `deleting` 时立刻 bump），使缓存 key 立即失效
2. 缓存命中后仍用权威 PG 校验 chunk/file 活性，无效则回源
3. 删除时按 `file_id` 主动淘汰相关 cache 条目（作为加速，不能代替 1 或 2）

### 验收

- [ ] 删除后立刻用原问题检索：结果不含该文件
- [ ] 删除后、cleanup worker 完成前，精确缓存不得命中旧证据
- [ ] 新检索路径仍然过滤非 `completed` 文件
- [ ] 回归：知识版本 bump 后旧 cache key 不再命中（已有部分测例，需覆盖「先 deleting 再 bump」窗口）

## P1-CONTINUE-RAG 续写把合成 prompt 当作新问题做 RAG

- **模块：** Chat
- **位置：** `server/src/modules/chat/chat-stream.service.ts`（约 141–144、228–256、292–309 行）、`client/src/stores/useChatStore.ts`（约 611–625 行）、`server/src/lib/ragTrigger.ts`（`default_rag=true`）
- **关联：** `P1-CONTINUE-MERGE`、`P2-AGENT-CONTINUE`、`P2-CONTINUE-PERSIST`

### 场景

用户对已生成回答点 Continue。客户端发送 `Please continue your response...` 且 `continue: true`。服务端复用上一条 **user** 消息 ID（不落库新 user message），但 RAG 触发、`prepareGroundedAnswer`、grounded prompt 全部使用该合成 `content`。`shouldUseRagForMessage` 对这段英文续写走 `default_rag=true`。

### 根因

Continue 被实现成「再发一条特殊用户问题」，而不是「在同一助手消息上续写」。RAG 层看不到 `continue` 语义。

### 预期

- 普通聊天 Continue：跳过 RAG 触发，用原问题/原证据续写，或明确禁用 RAG
- Agent 会话：禁用 Continue（见 `P2-AGENT-CONTINUE`），因为 Agent 是整轮工具循环 + 一次性落最终答案
- 合成 prompt 不得写入 `messages`（见 `P2-CONTINUE-PERSIST`）

### 建议改法

服务端 `continueGeneration=true` 时 `shouldRunRag = false`，续写只基于已有助手内容与历史。客户端 Agent 模式隐藏 Continue。

### 验收

- [ ] 开启 RAG 的会话点 Continue：不再出现新的 ragRun / 错误检索拒答
- [ ] 服务端测试：`continue: true` 不调用 `prepareGroundedAnswer`
- [ ] Agent 会话 UI 无 Continue；若请求带 `continue` + `agent_id`，服务端拒绝

## P1-FIRST-SEND 无会话时首次发送可双发且创建失败无 toast

- **模块：** Frontend
- **位置：** `client/src/pages/Chat.tsx`（`handleSendMessage`，约 198–217 行）、`client/src/stores/useChatStore.ts`（`createConversation`，约 192–284 行）

### 场景

空会话输入框连点发送，或创建会话接口失败。

### 根因

1. `createConversation` 在 `try` 外；失败变成未捕获异常，无 toast，草稿可能已清
2. 创建过程中 `sendingMessage` 仍为 `false`，提交按钮仍可用，可创建两个会话并打到乐观 `temp-*` ID
3. `createConversation` 成功后 **不等待** `selectConversation`（fire-and-forget）。随后 `sendMessage` 写入乐观消息，异步 fetch 可能用服务端欢迎消息覆盖

### 预期

- 创建中禁用发送
- 创建失败 toast，输入保留
- 只创建一个会话、只发一条消息
- `selectConversation` 不得冲掉进行中的流式乐观消息

### 建议改法

把创建纳入同一 try；创建期间设 sending/lock；`sendMessage` 直接使用 `createConversation` 返回的 id；`selectConversation` / `fetchConversationMessages` 在有活跃 stream controller 时不要覆盖缓存（部分逻辑已有，需覆盖「刚从 tempId 换成真实 id」）。

### 验收

- [ ] 连点发送只产生一个会话、一条用户消息
- [ ] 创建 500 时有错误 toast，输入框内容还在
- [ ] 首条消息流式过程中列表不会被欢迎消息替换成空白

## P1-SSE-RECOVER Agent SSE 断线后不会自动恢复轮询

- **模块：** Frontend / Agent
- **位置：** `client/src/pages/Chat.tsx`（约 106–124 行）、`client/src/stores/useChatStore.ts`（SSE 处理，约 898–913 行）
- **文档承诺：** `docs/agent-platform.md` 第 5 点「SSE 断线或页面重载后聊天页会从数据库恢复」

### 场景

Agent 运行中网络/代理断开 SSE，页面未整页刷新。服务端 Run 仍在跑（这是有意设计）。

### 根因

恢复轮询只看 `message.agent_run_status ∈ {queued, running, waiting_approval}`。直播 SSE 只写 `agentRunId` / `agentEvents`，**不写** `agent_run_status`。断线后 `sendingMessage=false` 且 status 仍空 → `hasRecoverableAgentRun=false` → 不轮询。整页刷新走 messages API 才带 status。

运行记录页也不轮询活跃 Run（`P2-RUN-HISTORY-POLL`），用户切到「运行记录」同样看不到自动更新。

### 预期

SSE 不完整结束后：

1. 若本地已有 `agentRunId` 或未终态 `agentEvents`，启动与聊天页相同的 1.5s 轮询
2. 轮询拉到终态/审批后更新时间线
3. 不得自动 cancel Run
4. 错误 toast 不应诱导用户「再发一条」造成重复用户消息（可提示「已从服务器恢复」）

### 建议改法

SSE 写入 `agent_run_status: 'running'`；或 `hasRecoverableAgentRun` 同时看 `agentRunId` + 无 `run.completed`/`run.failed`/`run.cancelled`。`refreshMessages` 在 stream 已结束后必须真正打 API。

### 验收

- [ ] 模拟 SSE abort：不刷新页面，数秒内时间线继续更新直到完成或等待审批
- [ ] 整页刷新仍能恢复（回归）
- [ ] 不会因为 toast「可重试」而自动或轻易重复发送用户消息

## P1-CONTINUE-MERGE Continue 合并两条助手消息，删除会删错段

- **模块：** Frontend
- **位置：** `client/src/components/MessageList.tsx`（约 56–89、165–167 行）、`client/src/components/ChatMessage.tsx`（删除，约 356–363 行）
- **关联：** Continue 会插入连续两条 `assistant`（`useChatStore.ts` 约 728+）

### 场景

普通聊天续写后，列表把连续两条 assistant 合成一条显示。`key` 和 `onDelete` 使用 **第一条** id。

### 根因

`MessageList` 为了「防止重复」合并相邻 assistant。Continue 的两条消息是合法的独立持久化记录，不是重复。

### 预期

独立助手消息不得合并。若产品希望视觉上像一段，删除必须针对「合并组最后一条」或提供分别删除。推荐：**不要合并**。

### 建议改法

删除相邻 assistant 合并逻辑，或仅合并仍是乐观数字 id 的流式占位。删除/分支/复制使用真实 message id。

### 验收

- [ ] Continue 后可见两段助手消息（或明确的分段 UI），各有自己的删除
- [ ] 删续写段不影响原文；删原文不影响续写段（按产品选择，但绝不能「点删却删另一条」）
